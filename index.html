MIPSpro software pipelining on r9999

135 TSVC kernels compiled by MIPSpro 7.30 for the R4000, with software pipelining on and off, run on the r9999 out-of-order MIPS core. Overall, SWP is a wash. The kernels where it isn't are explained by two mechanisms in the core, not by the quality of MIPSpro's schedules.

Setup

  • Compiler: MIPSpro 7.30 f77 -n32 -mips3 -r4000 -O3, with and without -SWP:=OFF, run inside IRIX 6.5 under emulation. The source is the Fortran TSVC "vectors" suite (loops.f, mains.f).
  • Harness: the MIPSpro .o files are linked bare-metal with GNU ld through a small n32 shim (harness/): symbol-table fixup, crt0, linker script, and a runtime that times each kernel with CP0 Count. The driver is generated from mains.f with n=100, ld=1000, ntimes=100.
  • Core: the r9999 ooo_core Verilator model with a 32-entry ROB, 512 KB L2 and 37-cycle memory latency (matching the silicon DRAM latency), 1 FP pipe, 1 load/store pipe, and an 8-entry LSU.
  • IPC: instructions per kernel come from the interp_mips ISS, whose Count advances once per instruction. Cycles = 2 × the RTL's Count, which ticks every other cycle. Checksums are identical with and without SWP on all 135 kernels.

Reading the pipetraces

Each pipetrace page covers 420 retired instructions from the kernel's steady-state loop. F = fetch, A = allocate, C = complete, R = retire. The memory-pipe events are: Q = enters the LSU, S = LSU issue, H = L1D hit, Z = store data captured, K = wakeup. The excerpts below are generated by tools/dumprec, with cycles relative to the first fetch.

1. s318: a not-taken branch-likely always restarts

s318 is isamax, a max-abs reduction with an index. The R4000 has no conditional moves, so MIPSpro if-converts it with branch-likely as a predicate. bc1tl .+8 executes its delay slot only when the condition is true, and the next PC is the same either way:

c.lt.s  $f1,$f2
bc1tl   .+8          # if fcc: run the delay slot
mov.s   $f1,$f0      # predicated update of max

In r9999, a branch-likely that is not taken nullifies its delay slot by restarting the pipeline (t_mispred_br = ... || !t_take_br in exec.sv). The predicate is almost always false for a max reduction, so all four steady-state bc1tl restart on nearly every execution: 4900 times each, about 20K mispredicts in total against 109 without SWP. No branch predictor can avoid this, because the restart happens whatever the prediction.

8002cff8  bc1tl 0x8002d000   F   1 A   6 C  13 R  15
8002d000  addiu $at,$at,1    F  18 A  25 C  29 R  30     <- fetch restarts after the bc1tl resolves
8002d008  bc1tl 0x8002d010   F  19 A  26 C  30 R  31
8002d010  beq $a1,$at,...    F  34 A  40 C  44 R  45     <- and again

That works out to about 36 cycles per element with SWP, against about 6 without. The no-SWP loop uses ordinary bc1f branches, which the predictor learns. s3110, s273 and s315 lose the same way.

2. vas: SWP puts the store addresses on the critical path

a(ip(i)) = b(i) is a scatter with no branch-likely and 11 mispredicts. Without SWP it takes 16 cycles per 4 elements; with SWP it takes about 19. MIPSpro's own R4000 estimate for its schedule was 21 cycles per 4 iterations.

Two LSU properties combine here:

  • No load-past-store speculation. A load may not issue while any older store hasn't done its address pass, so in practice memory ops issue in program order, one per cycle.
  • An 8-entry LSU in which a store holds its slot until it retires and commits.

The SWP code issues 8 loads (4× b, 4× ip), then 8 sll/addu to form the addresses, then 4 stores. The loads fill the LSU and the mem uop queue, so in-order allocation stalls and the address arithmetic is allocated late. The stores' addresses are therefore late, and the next group's b loads, whose addresses are already known, wait behind those stores:

80037ebc  lwc1 $f0, ($a2)       F   3 A   8 C  19   Q15  S16  H18
80037ec0  sll $at, $at, 2       F   4 A  13 C  17                 <- fetched at 4, allocated at 13
 ...
80037edc  addu $at, $t0, $at    F   7 A  17 C  24
80037ee0  swc1 $f0, -4($at)     F   8 A  17 C  26   Q18  Z21  S23  <- address pass waits on the addu
 ...
80037ef8  lwc1 $f2, 0x1c($a2)   F  17 A  20 C  31   Q23  S28  H30  <- known address, still waits for the older stores

The no-SWP code has the same instructions interleaved (lw, sll, addu, lwc1, …), so each store's address is ready almost as soon as its data and the LSU keeps flowing. s491, also a scatter, loses 1.12× and is probably the same story.

3. s241: SWP wins by not clogging the LSU

a(i) = b(i)*c(i)*d(i); b(i) = a(i)*a(i+1)*d(i). SWP runs it 1.56× faster with the same instruction count and essentially the same mispredicts (9 against 10): about 10 cycles per element against 17.5.

The no-SWP loop is unrolled 4×: 16 loads, then 16 mul.s in 3-deep chains, then all 8 stores at the bottom. The stores' data arrives only when the multiply chains finish, and each store keeps its LSU slot until it commits, so the 8 stores fill all 8 slots. The next trip's first load is allocated at cycle 59 but doesn't enter the LSU until cycle 81, and consecutive trips never overlap:

8001af54  swc1 $f7, -0x14($a1)  F  53 A  57 C  64 R  78   Q60  S61  Z64
8001af5c  swc1 $f3, -0x14($a0)  F  55 A  59 C  65 R  79   Q61  S62  Z76   <- data waits on the mul chain
8001aeac  lwc1 $f12, 8($a2)     F  56 A  59 C  85 R  86   Q81  S82  H84   <- next trip: 22 cycles to get an LSU slot

MIPSpro's schedule (25 cycles per 2 iterations, bound by the R4000 FP multiplier) has each stage store values computed by the previous stage. Store data is ready as soon as the store reaches the LSU, stores drain quickly, and loads get a slot about 2 cycles after allocation:

800220ec  swc1 $f1, 4($a1)      F   3 A  10 C  17 R  22   Q13  S14  Z19
800220f0  lwc1 $f1, 0x14($v1)   F   4 A  11 C  18 R  23   Q14  S15  H17
800220f8  swc1 $f0, 8($a1)      F   6 A  12 C  19 R  24   Q15  S16  Z20

Conclusions

Branch-likely. The largest SWP losses all come from the not-taken branch-likely restart. MIPSpro uses b*l .+8 as predication for R4000. To make this cheap, the delay slot of a likely branch could be renamed as a predicated op that selects the old destination register when the branch is not taken, instead of flushing.

LSU. vas (an SWP loss) and s241 (an SWP win) are the same bottleneck viewed from opposite sides: an 8-entry LSU where each store holds its slot until commit, combined with no speculation of loads past unresolved store addresses. Freeing a store's LSU slot when it moves to the store buffer, or adding memory-dependence speculation, should give the no-SWP code most of s241's gain and remove vas's loss. That is also a likely contributor to the low base IPC (geomean 0.8).
